# Map + Route Visualization

## Overview

The **Map + Route Visualization** module is responsible for displaying trip locations, itinerary stops, and travel routes on an interactive map.

This module is developed as an independent frontend feature under:

```text
src/features/mapRouteVisual/
```

The main responsibilities of this module are:

* Display an interactive map
* Visualize itinerary locations with markers
* Display location information through popups
* Visualize routes between itinerary stops
* Support real road-based routing
* Support multi-stop itineraries
* Automatically adjust the map viewport to the itinerary
* Integrate with itinerary data generated by other modules

The module is designed to remain independent from the internal implementation of the itinerary-generation system. It receives normalized trip/location data and handles its geographic visualization.

---

# 1. Technology Stack

## OpenStreetMap

**OpenStreetMap (OSM)** is used as the map data and tile source.

It provides the geographic map displayed underneath the route visualization.

Responsibilities:

```text
OpenStreetMap
      ↓
Base map / map tiles
      ↓
Roads, buildings, geographic context
```

Unlike Google Maps, displaying standard OpenStreetMap tiles does not require a Google Maps API key.

---

## Leaflet

**Leaflet** is the JavaScript mapping library responsible for rendering and interacting with the map.

Main responsibilities:

* Display map tiles
* Pan and zoom
* Display markers
* Display popups
* Draw polylines
* Control map bounds
* Handle map interactions

Conceptually:

```text
OpenStreetMap = map data / tiles

Leaflet = map rendering + interaction
```

---

## React-Leaflet

Because the frontend is built with React, **React-Leaflet** is used as the React integration layer for Leaflet.

Instead of directly manipulating Leaflet objects, the map can be constructed using React components such as:

```jsx
<MapContainer>
  <TileLayer />
  <Marker />
  <Popup />
  <Polyline />
</MapContainer>
```

Installation:

```bash
npm install leaflet react-leaflet
```

---

## OSRM

**OSRM (Open Source Routing Machine)** is used for road-based route calculation.

Leaflet itself does not calculate routes. It only renders geographic information.

OSRM receives coordinates such as:

```text
Harvard → MIT
```

and returns:

* Route geometry
* Distance
* Estimated travel duration

The returned geometry can then be rendered by Leaflet.

Architecture:

```text
Location coordinates
        ↓
       OSRM
        ↓
Route geometry
        ↓
React-Leaflet
        ↓
Polyline on map
```

For initial development, the public OSRM service may be used for prototyping. Production deployment may later require a dedicated or alternative routing service depending on usage requirements.

---

## Nominatim — Optional / Later Stage

**Nominatim** can be used for geocoding when itinerary data contains place names or addresses but does not contain coordinates.

Example:

```text
"Museum of Fine Arts, Boston"
            ↓
        Nominatim
            ↓
Latitude / Longitude
```

If the backend already provides latitude and longitude for every itinerary stop, this layer may not be necessary.

```text
                          │
                          ▼

                          │

                          ▼

                          │
```

```text
Place Name / Address

        ↓

        ↓

```

# 4. File Responsibilities

## `MapView.jsx`

Main entry component of the map feature.

Responsibilities:

* Create the Leaflet `MapContainer`
* Load OpenStreetMap tiles
* Render itinerary markers
* Render route layers
* Coordinate map-level components

Conceptually:

```text
MapView
├── TileLayer
├── StopMarker
├── StopMarker
├── StopMarker
└── RouteLayer
```

`MapView` should primarily coordinate visualization and should not contain routing API logic.

---

## `StopMarker.jsx`

Responsible for rendering individual itinerary stops.

Example:

```text
① Hotel
② Museum
③ Restaurant
④ Park
```

Each marker receives location information such as:

```js
{
  id: 1,
  name: "MIT",
  latitude: 42.3601,
  longitude: -71.0942,
  type: "attraction"
}
```

Future versions may use different marker styles for:

* Hotels
* Restaurants
* Attractions
* Airports
* Activities

---

## `MapPopup.jsx`

Responsible for displaying information when the user selects a marker.

Possible information:

```text
Museum of Fine Arts

10:00 AM – 12:00 PM

Visit museum exhibitions

View Details
```

Potential fields include:

* Location name
* Start/end time
* Description
* Activity type
* Image
* Additional details

---

## `RouteLayer.jsx`

Responsible for drawing routes on the map.

It receives route coordinates and renders them using Leaflet polylines.

Example:

```text
Stop 1
   ↓
Stop 2
   ↓
Stop 3
```

`RouteLayer` should not be responsible for requesting routes from OSRM.

Its responsibility is visualization only.

---

## `routingService.js`

Responsible for communication with the routing provider.

Initial routing provider:

```text
OSRM
```

Example responsibility:

```js
getRoute(start, end)
```

Input:

```text
Start coordinate
End coordinate
```

Output:

```js
{
  coordinates: [...],
  distance: 2400,
  duration: 1800
}
```

Keeping routing logic inside a service means the routing provider can later be changed without rewriting the Leaflet components.

---

## `routeUtils.js`

Responsible for route-related data transformations.

For example, given:

```text
A
B
C
D
```

it can generate:

```text
A → B
B → C
C → D
```

Possible utilities include:

```js
buildRoutePairs(locations)
```

and coordinate-format conversion functions.

---

## `geocodingService.js`

Optional future service.

Responsible for converting place names or addresses into coordinates using a geocoding provider such as Nominatim.

Example:

```text
"MIT, Cambridge MA"
        ↓
geocodingService
        ↓
42.3601, -71.0942
```

This service is only necessary if coordinates are not already supplied by the backend.

---

## `useRoute.js`

Possible future custom React hook.

Responsible for connecting React state with the routing service.

Example:

```js
const {
  routes,
  loading,
  error
} = useRoute(locations);
```

This keeps API loading/error state outside `MapView`.

---

## `useMapBounds.js`

Possible future hook responsible for automatically adjusting the map viewport so all itinerary stops and routes remain visible.

Example:

```text
Harvard
      \
       MIT
          \
           Downtown Boston
```

The map automatically determines the appropriate center and zoom level instead of relying on a fixed zoom.

---

## `mapConstants.js`

Possible future location for shared map configuration.

Examples:

```js
DEFAULT_MAP_CENTER
DEFAULT_ZOOM
OSM_TILE_URL
```

This prevents configuration values from being duplicated throughout components.

---

## `index.js`

Public entry point for the feature.

Other parts of the application should ideally import the feature through this file instead of depending on its internal directory structure.

For example:

```js
export { default as MapView } from "./components/MapView";
```

Then another module can use:

```js
import { MapView } from "./features/mapRouteVisual";
```

# 5. Development Plan

Development should proceed incrementally so that visualization, routing, and integration problems can be tested independently.

## Phase 1 — Basic Leaflet Map

### Goal

Display a functional interactive map.

### Tasks

* Install Leaflet
* Install React-Leaflet
* Create `MapView.jsx`
* Add `MapContainer`
* Add OpenStreetMap `TileLayer`
* Configure initial center
* Configure initial zoom
* Import Leaflet CSS

### Expected Result

A map that can:

* Display OpenStreetMap
* Zoom
* Pan

No markers or routes are required yet.

# 6. Phase 2 — Static Markers

### Goal

Display itinerary locations on the map.

Start with hardcoded development data:

```js
const locations = [
  {
    id: 1,
    name: "Harvard University",
    latitude: 42.377,
    longitude: -71.1167
  },
  {
    id: 2,
    name: "MIT",
    latitude: 42.3601,
    longitude: -71.0942
  }
];
```

### Expected Result

```text
● Harvard


             ● MIT
```

The implementation should already accept a location array rather than hardcoding individual markers inside the map component.

# 7. Phase 3 — Marker Popups

### Goal

Clicking a marker should display location information.

Example:

```text
MIT
```

### Expected Result

```text
Click Marker
     ↓

```

# 8. Phase 4 — Static Route Visualization

### Goal

Verify that route rendering works before introducing an external routing service.

Initially, directly connect coordinates using a Leaflet `Polyline`.

Example:

```js
[
  [42.377, -71.1167],
  [42.3601, -71.0942]
]
```

### Expected Result

```text
Harvard ●────────────● MIT
```

This route is not expected to follow real roads yet.

The purpose of this phase is to verify `RouteLayer.jsx` independently from OSRM.

---

# 9. Phase 5 — Automatic Map Bounds

### Goal

Automatically show the complete itinerary.

Instead of using a permanently fixed map center and zoom:

```text
Locations
    ↓
Calculate Bounds
    ↓
Leaflet fitBounds()
    ↓
All itinerary locations visible
```

The map should automatically zoom and pan whenever the displayed itinerary changes.

---

# 10. Phase 6 — OSRM Road Routing

### Goal

Replace straight-line routes with real road-based routes.

Flow:

```text
Harvard coordinates
        ↓
       OSRM
        ↓
Road route geometry
        ↓
   RouteLayer
        ↓
Leaflet Polyline
```

OSRM should also provide information such as:

```text
Distance: 2.4 km
Duration: 18 min
```

This information can later be displayed in a route information panel.

---

# 11. Phase 7 — Multi-Stop Itinerary

### Goal

Support a complete travel itinerary.

Example:

```text
Hotel
  ↓
Museum
  ↓
Restaurant
  ↓
Park
```

For locations:

```text
A, B, C, D
```

the module should generate route segments:

```text
A → B
B → C
C → D
```

Each route can then be requested and rendered.

# 15. Data Boundary with Other Modules

A key design principle is that the Map + Route Visualization feature should not need to understand how an itinerary was generated.

The system boundary should be:

```text
AI / Planner Module
        ↓
Backend
        ↓
Normalized Itinerary Data
        ↓
Map + Route Visualization
```

Ideally, every location passed to the map already contains:

```text
id
name
latitude
longitude
type
time / order
```

This reduces coupling between the map feature and the rest of the application.

If latitude and longitude are unavailable, geocoding can be added as an intermediate step.

# 16. Design Principles

### Feature Isolation

Map-specific code stays inside:

```text
features/mapRouteVisual/
```

Code should only be moved to global directories such as:

```text
src/components/
src/services/
src/hooks/
src/utils/
```

when it becomes genuinely shared by multiple features.

### Separation of Concerns

Components render UI.

```text
components/
```

Services communicate with external APIs.

```text
services/
```

Hooks manage React-specific state and lifecycle logic.

```text
hooks/
```

Utilities transform data.

```text
utils/
```

### Routing Provider Independence

Leaflet components should not directly depend on OSRM.

Instead:

```text
MapView
   ↓
useRoute
   ↓
routingService
   ↓
OSRM
```

This allows the routing provider to be replaced later without rewriting the map UI.
